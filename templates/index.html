How it's calculated

Memory

Every number starts from the VRAM the serving runtime can actually touch, then subtracts what is spoken for before any request arrives.

Usable VRAM
GPUs x GPU memory x VRAM util — the utilization factor is the share the runtime is allowed to allocate (vLLM's gpu_memory_utilization).
Weights
params (B) x bytes per weight — total parameters, not active ones, because all experts of a mixture-of-experts model still occupy memory.
Free for KV
usable VRAM - (overhead x GPUs) - weights, floored at zero. This is the pool every concurrent request competes for.
KV per request
The KV cache for one sequence at the given context length, multiplied by the KV fragmentation factor, plus any fixed recurrent state the architecture keeps. Context length here is input + output.
Footprint
weights + overhead + (concurrent users x KV per request). Fits is a comparison of this against usable VRAM.
Concurrent capacity
floor(free for KV / KV per request), evaluated both at your workload context and at the model's maximum context window.

Latency

These are roofline estimates: prefill is compute-bound, decode is memory-bandwidth-bound, and both use active parameters so mixture-of-experts models are not over-penalized. Multi-GPU scaling is discounted for tensor-parallel communication (85% at 2 GPUs, 75% up to 4, 65% beyond).

Prefill per token
2 x active params (B) / (effective GPUs x FP16 TFLOPS) in ms, scaled by batch size.
TPOT
Time per output token: bytes per weight x active params (B) / (effective GPUs x bandwidth GB/s) in ms, scaled by batch size. The batch-1 figure is the same formula without that scaling — a best-case ceiling.
TTFT
Time to first token: (input x prefill per token + TPOT) / 1000 seconds.
E2E
(input x prefill per token + output x TPOT) / 1000 seconds.
Throughput
concurrent users x output tokens / E2E — aggregate output tokens per second across the batch, not per user.

Latency cells read INFEASIBLE when the configuration does not fit in memory; there is no meaningful speed for a deployment that cannot start.

KV cache by architecture

KV size is where model families diverge most, so the calculator branches on architecture. The baseline shape is 2 x layers x KV heads x head dim x bytes x tokens — the 2 covers keys and values.

Standard
Every layer caches the full sequence. Grouped-query attention is already reflected in the KV head count, which is why an 8-KV-head model caches far less than its 64 attention heads suggest.
Hybrid sliding
Only a few layers attend globally; the rest use a sliding window and cache at most min(context, window) tokens. Growth past the window is therefore driven by the global layers alone. Some models also share one cache across a group of global layers, which divides that portion further.
Qwen3 hybrid
Roughly one layer in four is real attention and caches the full sequence; the remaining layers are gated linear-attention blocks whose recurrent state is a fixed heads x head dim x state dim tensor per layer. That state is added per request but does not grow with context, so long contexts cost a fraction of a standard model.
MLA
Multi-head latent attention stores one compressed latent per token instead of per-head keys and values: (KV LoRA rank + RoPE head dim) x bytes per layer, with sliding layers still capped at the window. This is the smallest per-token cache of the four.
Multimodal
KV math follows the standard path — image and video tokens land in the same cache once encoded. The weight figure includes the vision tower, and remember that a single image can expand to hundreds or thousands of tokens, so raise the input length rather than expecting a separate adjustment here.

Reading the tables

Each table shows the decision-critical columns by default. Details reveals secondary columns — maximum-context figures, batch-1 ceilings, raw token counts — for every row at once so they stay comparable. Copy JSON exports exactly the columns you can see. Hover or focus a column header for a one-line definition.

All of this is a first-order model, not a benchmark. It ignores activation memory, CUDA graph padding, chunked prefill scheduling, speculative decoding and real-world queueing. Treat the output as a shortlist of viable configurations to test, not a promise.
